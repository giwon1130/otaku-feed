# 백엔드 서비스 종료

> **누가 봄**: DevOps, 향후 재가동 검토자
> **언제 봄**: 종료 진행 / 재가동 시
> **종료일**: 2026년 4월 (Railway 비용 문제)

## 결정 배경

- 사용자 수 적음 (개발자 본인 + 소수)
- Railway Hobby 플랜 + PostgreSQL add-on 고정 비용 (~$5–10/월)
- 데이터 가치 평가: **재생성 가능** (좋아요 다시 모으면 됨)
- 클라이언트 자체는 비로그인(로컬-only) 모드로 모든 기능 동작

→ 백엔드 서비스만 종료, 클라이언트 앱은 로컬 모드로 유지.

## 종료 절차

### 1. 클라이언트 코드 정리 (✅ 완료)
- `App.tsx` + `src/storage.ts`에 `BACKEND_ENABLED = false` 플래그
- 로그인/로그아웃 버튼 숨김 (메뉴에 "로컬 모드" 안내)
- `useBackendHealth` polling 비활성
- `apiHealth`/`apiMe`/`loadPrefs` 등 모두 호출 스킵
- swipe 큐 push (`flushPending`) no-op

→ 풀빌드 또는 EAS 빌드로 폰에 반영.

### 2. Railway 종료 (사용자 직접)

**옵션 A — 일시 정지 (권장 첫 단계)**
- Railway 대시보드 → otaku-feed-api → Settings → **Pause**
- 컨테이너 stop, 비용 0
- DB는 유지 (혹시 모를 복구 대비)
- 마음 바뀌면 즉시 재시작 가능

**옵션 B — 완전 삭제 (일주일 후 결정)**
- Railway 대시보드 → 프로젝트 전체 → Settings → **Delete Project**
- 컨테이너 + DB + add-on 모두 삭제
- 데이터 영구 손실

### 3. 외부 서비스 정리 (선택)
- **Apple Developer**: 유지 — 앱 자체는 계속 사용
- **expo.dev**: 유지 — EAS Build에 사용 가능
- **Kakao/Google OAuth**: 유지 — 향후 다른 백엔드(Supabase 등)로 이전 시 재사용
- **DeepL API key**: 유지 — 클라이언트가 계속 번역 사용 (비용 0, 무료 한도 내)

## 재가동 절차 (혹시 마음 바뀌면)

### 같은 백엔드 (Railway 재시작)
- Railway 프로젝트 Resume (옵션 A에서 멈췄을 때)
- 이 문서의 "클라이언트 코드 정리"를 reverse:
  - `src/storage.ts`의 `BACKEND_ENABLED = true`
  - `App.tsx`의 `BACKEND_ENABLED = true`
- 풀빌드 → 배포

### 다른 백엔드 (Supabase 등 무료)
별도 마이그레이션 작업 필요. ADR로 결정 기록.

핵심 작업:
- Supabase 프로젝트 생성 + Auth + DB 셋업
- `src/api/otakuApi.ts`를 Supabase JS SDK로 교체
- 동일 schema (otaku_users / otaku_user_prefs / otaku_user_swipes)
- 다시 위 `BACKEND_ENABLED = true`

예상 공수: 4–6시간

## 영향

| 사용자 경험 | 변화 |
|---|---|
| 첫 부팅 | 동일 (장르 → 취향 분석 → 메인) |
| auth 단계 | 사라짐 — 바로 메인 |
| 헤더 | "로그인" 버튼 → "메뉴" 버튼 |
| 헬스 배지 | 사라짐 |
| 좋아요/패스 | 정상 동작 (로컬 저장만) |
| 다른 디바이스 동기화 | 안 됨 |
| 검색 / 디테일 / 라프텔 / 번역 | 모두 정상 (외부 API 그대로) |

## 안 한 것

- ❌ DB 백업 (가치 없음으로 판단)
- ❌ otaku-feed-api 레포 archive (코드는 보존)
- ❌ 앱 자체 종료 (계속 본인용으로 사용)
